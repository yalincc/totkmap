## 一、为什么越修补问题越多？三层根因

### 表层：补丁式演进，每个补丁救一个场景、伤一个场景

| 轮次 | 想解决 | 补丁 | 踩出的新坑 |
|---|---|---|---|
| round1 | 站桩时误锁 170m 外 NPC | pool-follow 加"玩家最近 5s 有位移"前置 | 玩家**走动中槽轮换**时锁读数不变 → 前置误判"站桩" → 接管被挡 → **卡死** |
| round2 | 修卡死 | 删前置 | known 快路径池空 + `!verified` 挡住共识 → **永久卡死**（无恢复路径） |
| round3 | 修永久卡死 | 删 `!verified` 前置 + 池活动旁证 | 站桩 verified 锁每 45s 误重扫（旧病复发）→ 用 poolAnyMove 豁免解决 |

教训：每个补丁都基于"当前观察"打局部判断，没有回到模型层面想"判活到底该怎么判"。

### 中层：单一信号源——所有推断都押在"锁读数"上

状态机里 6 套机制（scan/probe/known-watch/pool-follow/consensus/静止确认）全部围绕锁读数推断，但锁读数噪音极大：

- **读数冻结** ≠ 站桩（也可能是副本轮换）
- **读数在动** ≠ 玩家（也可能是 NPC/粒子/动画槽）
- **读数跳变** ≠ 传送（也可能是场景切换垃圾）

### 深层：缺"判活模型"——位置一致性 > 移动性

所有坑的共同错误假设：**"在动的地址 = 玩家"**。
正确模型：**"在动"只是必要条件，"在动且位置连续（距上次玩家位置近）"才是玩家证据**。

- round1 NPC 槽在动但距玩家 170m → 300m 闸门放行 → 误锁
- round2 玩家在动的证据只来自锁读数 → 轮换期读不出 → 卡死
- 最终靠 poolFollowNear=15m + 池活动旁证把"位置一致性"立起来

**凡是用"动"直接判活的，都踩坑；凡是用"动+位置连续"判活的，都稳定。**

## 二、定位大逻辑（修复后收敛的正确模型）

```
[存档锚点]  slot_00 权威 + 800m 聚类剔除污染槽（神庙坐标距主簇 1603m 必剔除）
    ↓
[窗口扫描]  以锚点为圆心 ±120m，找 copies+struct 高组（玩家副本簇特征），
            占位池黑名单（copies>18000 无结构/三值相等/原点小值/北轴近零）先过滤
    ↓
[锁定]      candidate：copies 数百 struct>0，距锚点近
    ↓
[判活·三选一]
  ├─ 移动确认：玩家动，槽跟随 3 拍位移 >0.5m → verified
  ├─ 静止确认：玩家站桩，冻结 10s + 副本簇（≥3 一致成员 <15m）→ verified
  └─ 都不满足 → 30s 冻结共识（找 ≥3 一致簇）→ 有活簇换锁 / 无簇重扫（90s 冷却）
    ↓
[副本轮换接管]  锁冻结 ≥3tick + 池内 15m 内活副本连续动 2 拍 → 接管
                （位置闸门 15m 防 NPC；池活动 poolAnyMove 作站桩旁证）
    ↓
[场景检测]     神庙本地坐标（|X|<200, |Y北|<200, alt<-50）→ /pos 输出入口坐标，
               source=shrine-hold，红点停门口；出神庙自动恢复
    ↓
[/pos 输出]    X / Y北 / alt + verified + layer + source
```

### 四条铁律

1. **位置一致性 > 移动性**：候选必须距玩家 15m 内，"在动"不是玩家证据
2. **站桩不是错误**：冻结时先问"池在动吗"，池静止 = 站桩 = 正常，不换锁不重扫
3. **多信号源交叉**：锁读数 + 池活动 + 副本簇 + 锚点，单一信号不决策
4. **重扫要冷却（90s）+ bypassKnown**：防锁回死槽、防扫描风暴
