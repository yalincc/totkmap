## 二、V1.1 修复历程（时间线）

### 2.1 问题③性能——最先破案（OOM 根因）
- 现象：启动定位后引擎崩溃（`fatal error: out of memory`，xnavi-gui-core.log:12910），用户体感"开了定位有点卡"。
- 根因：扫描 16 workers × 64MB 缓冲 = 1GB 峰值内存；当时系统 31.8GB 内存空闲仅 0.6GB（eden 独占 23.5GB）→ 直接 OOM 崩溃。
- 修复：chunkSize 64→8MB、workers 16→6、scanAll 跳过 ≥2GB 巨型块（DRAM 主映射区，省 60% 扫描量）。
- 验证：重建后引擎 WS 仅 16-20MB，扫描 10-11s 完成不崩。

### 2.2 日志超长
- 现象：每次扫描 ~1.7MB 日志（locate.go 把全部 28758 个 region 逐行打印）。
- 修复：改 top10 + "... N more regions"。

### 2.3 坐标口径三重验证（铁证）
- 对照：游戏右上 mod 调试面板 POS、右下 HUD、内存原始三元组。
- 结论：游戏/HUD 序 (X东, Y北, Z高)；内存原始 (X, Z_stored=高度+105, Y北)；elevBias=105.0。

### 2.4 神庙锁定铁证（quickwatch 探针采样）
- 采样 30 拍 × 400ms，10 个候选地址：
  - 真玩家槽 0x024E9782F0F0：坐标平滑变化 (28.5→56→60→66)，跟随玩家轨迹。
  - 引擎反复锁的死槽 0x24E79F03970：(20,1510,1480) 全程不动。
  - 其余地址为 0 / 垃圾 / 闪变（2128m 级跳变）。
- **结论：Eden 下玩家坐标在多个副本地址间轮换更新——单一地址会冻结，簇内其他地址活着。**
- 这是"锁死槽不跟玩家"问题的机制根因。

### 2.5 pool-follow 单地址移动接管（验证通过 ✅）
- 机制：锁读数停滞 ≥3 tick（~1.2s）→ 扫候选池（known 记忆 + 扫描 shortlist），位移 ∈(0.5,100)m 且连续 ≥2 次的地址判活副本 → 立即接管换锁（不要求 ≥3 一致簇，因为真槽副本常不足 3 个）。
- 配套：位置接近闸门 <300m（防远处垃圾区 0x2AE5 闪变地址）；接管后重新走移动确认（防垃圾地址污染 verified）。
- 验证：15:25-15:26 实测 3 个地址轮换接管、坐标 (30.6,-1491)→(92.4,-1543) 平滑跟随、全程无飘坐标。

### 2.6 probeCopyKeep 0.7→0.1
- 根因：Eden 下存档镜像簇 copies 可能大于真槽，0.7 比例门槛把真槽换锁全卡死。
- 修复：放宽到 0.1。

### 2.7 场景切换垃圾跳变防护（部分有效）
- 现象：进/出神庙时锁地址读到"合法范围内的垃圾坐标"，verified 锁的大位移被无条件当传送接受 → 红点飘地下/天空。
- 修复：大位移时 knownPool 交叉验证——新位置 100m 内有 ≥1 活副本 = 真传送（接受）；无副本 = 垃圾跳变（保持旧输出 + 累积 invalid → 快速重锚）。
- 结果：真传送（cross-verify）路径合理，但**场景切换后副本全失效时交叉验证无副本可查，仍会锁到垃圾**（见问题清单 P0）。

### 2.8 占位 Actor 池过滤（新增）
- 现象：rescan 锁到 copies=21044659 struct=190089 的全零槽（Eden 大量未使用 Actor 槽：结构完整但坐标全零，copies 千万级排第一）。
- 修复：scanRegion 过滤近零坐标三元组（|x|<5 && |y|<5、Z_stored<5）；锁定前 decodePos 校验候选（无效则 fallback 到 ranked 里第一个有效组）。
- 结果：全零槽不再被锁；但**"坐标合法但未初始化"的槽（如 (-8,8,-105)，Z_stored=0）仍可能通过**（Z_stored 近零过滤已补，待验证）。

### 2.9 解锁重扫 20s 冷却
- 现象：锁垃圾 → invalid → UNLOCKED → 立即重扫 → 再锁垃圾 → 循环风暴（实测引擎 WS 飙 2.6GB，一直 "locating"）。
- 修复：goUnlocked 后 20s 内不自动重扫（场景加载期跳过；真迁移靠 frozen → reLocateCooldown 重锚兜底）。

### 2.10 frozen 共识候选 dead 超时重扫
- 现象：frozen 共识找到候选（如 2m 处死槽）→ watching → 候选不动 → 永久等待（不换锁也不重扫）。
- 修复：候选 watching 15s 不动 = 死候选 → 强制重扫（bypassKnown 防锁回）。

## 三、当前问题清单（未解决）

### P0 阻塞：场景切换（进/出神庙、传送）锁定不稳定
- 现象链（15:30-15:34 实测）：
  1. 进神庙：坐标副本切换 → 锁冻结 → 红点停在神庙外位置（不跟随到庙内）。
  2. 出神庙：rescan 反复锁到未初始化垃圾槽（(-8,8,-105)、(12,-12,-93)，Z_stored=0）→ 红点漂地下/天空。
  3. 锁垃圾 → invalid → 解锁 →（旧版）立即重扫 → 再锁垃圾 → 循环；GUI 显示"一直验证移动 / locating"。
- 根因：场景切换期间 Eden 内存布局剧烈变化，**副本簇整体失效**，池内无活地址可接管；扫描排序（copies）被占位池污染，锁定候选质量无法保证。

### P1：known 绝对地址跨场景不可靠
- known_addrs.json 记忆的地址（known 快路径秒锁的依据）在场景切换后变死槽（读数静止），known 列表其他地址也同批失效 → known 秒锁直接锁死槽 → 卡 pending。
- 跨游戏重启的地址复用（V1.0.0 发现的"旧槽复活"）只在部分场景成立。

### P1：占位 Actor 池 copies 膨胀污染排序
- Eden 未使用 Actor 槽 copies 可达千万级（vs 真槽 2-4 万），struct 检测（rotOK）误报 19 万 → copies/struct 排序永远第一。
- 已加近零 + Z_stored 过滤，但"坐标合法但未初始化"的中间态垃圾仍可能漏网。

### P1：pool-follow 位置闸门误吞近零镜像簇
- 位置闸门 <300m 挡不住"近零坐标镜像簇"（如 X=0.1 的存档镜像/占位簇），短暂接管后又切回——不稳定抖动来源之一。

### P2：地图网页打开不直接缩放跟随
- 协议文档（BOTWmap导航配合接口协议-URL带参与进度契约-v1）已确认：GUI 拼 `?follow=1&game=totk`、网页 V1.9.2 已消费；缺口 = 网页端首次打开不缩放（followCenter 只范围平移不 zoom）。
- 属 TOTKmap 网页改动（js/live.js + V1.9.3 + 左下角版本号），待用户确认后执行。

### P2：性能体感验收
- OOM 根因已修（引擎 WS 16-20MB 稳定），但用户"开了定位有点卡"的体感尚未最终确认消除。

## 四、根因分析：Eden vs Ryujinx 的本质差异

| 维度 | live-go（Ryujinx 期假设） | Eden 实测 |
|---|---|---|
| 玩家坐标槽 | 单地址稳定、copies 最大 | 多副本地址轮换更新，单地址会冻结，簇内其他地址活着 |
| known 记忆复用 | 跨重启/跨场景可用 | 跨场景变死槽，只部分跨重启可用 |
| 占位 Actor 池 | 少量、copies 小 | 海量（19 万 struct 槽），copies 千万级污染排序 |
| 场景切换内存 | 相对平稳 | 布局剧烈变化，副本簇整体失效（数秒） |
| 未初始化槽 | 坐标全零易识别 | 中间态垃圾（坐标"合法"但 Z_stored=0 等） |

**核心结论**：live-go 的"找稳定单地址 + copies 排序 + known 记忆"整套思路在 Eden 下不成立。**Eden 需要"活副本池动态跟随"思路**：不追求单地址稳定，而是持续维护一组活地址，谁动读谁、谁冻结换谁。

## 五、后续方向（换思路候选）

### A. 活副本池动态跟随（推荐）
- 不再追求"锁定单个稳定地址"。锁定后维护 30-50 个活地址池，每拍（~200ms）采样全部：
  - 输出"池内连续移动一致簇"的均值/代表；
  - 地址冻结 → 标记失效，池内其他移动地址接管；
  - 场景切换（全池失效）→ 立即触发重锚（不等 30s frozen）。
- 优点：天然适配副本轮换；场景切换恢复最快。
- 风险：池维护复杂度；垃圾地址误入池。

### B. cheat 指针链（备选调研）
- bad1dea/NXCheats TOTK cheat（BID 9B4E43650501A4D4）指针链基于游戏 main 模块偏移，跨模拟器通用（Ryujinx/Yuzu 系）。
- Eden 是 Yuzu 系分裂，指针链大概率可用；需要读 main 模块基址 + 偏移。
- 优点：指针链稳定（模块内偏移不随场景变化）；缺点：需要逆向确认偏移在 Eden 下仍成立（曾发现 cheat 绝对地址失效）。

### C. mod 坐标源（备选）
- 用户 mod（UltraCam 等）已显示实时 POS——mod 本身读取了某个稳定源。
- 反推 mod 读的地址/模块偏移，或与 mod 作者仓库对照（NXCheats 同源）。
- 优点：稳定；缺点：依赖第三方 mod 内部实现，需逆向。

### D. 扫描策略改进（与 A 配套）
- 候选排序改为"活性 + 位置合理性"（移动一致性 + Z_stored 合理区间 + 结构特征），不再依赖 copies；
- 场景切换检测：锁读数冻结 + 池内无移动地址 → 立即重锚；
- 占位池/未初始化槽过滤继续加固（Z_stored 区间校验：真实玩家 Z_stored ∈ [~100, ~3500]，排除 0 与异常）。

**建议路径**：A + D 组合（活池跟随 + 扫描质量改进）作为主攻，B（cheat 指针链）作为并行调研方向（低成本验证：读 Eden main 模块基址 + cheat 偏移表，看是否命中玩家坐标）。
